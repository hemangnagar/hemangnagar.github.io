Demo runbook · governed data platform

SAPIENT: reading the standard the sensors speak, and writing it back

Twenty minutes, three files. A capture in the UK MOD's open sensor standard; the enriched record an analyst made from it; and the same governed corpus projected back into that standard, once per recipient, so a fusion node consumes what it is entitled to with no translation step in front of it. Every figure here was captured from the deployed container on 2026-08-20.

counter_uas_sapient.bin · SAPIENT capture · 556 KB counter_uas_detections.csv · the enriched record two .bin files you make on stage · the point of the whole thing

The story in one paragraph

BSI Flex 335 — SAPIENT is Dstl's open standard for networks of autonomous sensors: edge nodes register with a fusion node and then report what they detect. It is freely published, its .proto files and reference middleware are Apache-2.0, and NATO is adopting it as the counter-UAS interoperability standard. So the interesting question is not whether this platform can read a drone detection — it is where a governance platform sits in a sensor network. The answer this demo gives: between the sensors and the fusion node, speaking the standard in both directions, deciding what each recipient receives rather than handing over a file and trusting them to redact it.

Before you start. Open http://127.0.0.1:8092 and log in. The two counter-UAS profiles ship unapproved on purpose — approving one live is a good thirty seconds, not a fault. Do not pick a local model from the analyst dropdown while presenting over the public tunnel: it takes about 394 seconds and Cloudflare cuts the response at 100.

Say where the field names came from, because this is the part that is different from every other format the platform reads.

object_id                    CEJZ05XHT5GMEJ146S6JR410DD
location_x                   -97.23268    ← longitude
location_y                    26.9091     ← latitude
location_z                   158.496
location_coordinate_system   LOCATION_COORDINATE_SYSTEM_LAT_LNG_DEG_M
location_datum               LOCATION_DATUM_WGS84_E
detection_confidence         0.96
object_info_sensor_modality  RF
object_info_cooperative      true      ← it identified itself
object_info_id_type          remote_id_serial
classification               Air:0.81
behaviour                    Approaching:0.83
signal_0_centre_frequency    2436999936
id                           1596F6090228

Four of those columns are not fields in the standard at all. object_info is a repeated {type, value} pair — SAPIENT's declared extension point, whose vocabulary each node registers up front — and the reader turns the type into the column name. So a sensor saying type: "cooperative", value: "true" arrives as a governable column with nothing written in Python. That is how a use case adds a field to this platform.

What to say

“The other two binary formats we read needed somebody to sit down with a specification and type out a JSON table of what each tag means. That table is a place errors live silently. SAPIENT ships its own schema — so we vendored the .proto files verbatim, Crown copyright notice and all, and the decoder runs off a descriptor compiled from them. There is no hand-written field table here to drift out of date, and no generated code in the tree either. Upgrading to the next BSI Flex version is dropping in new .proto files.”

“location_x is longitude and location_y is latitude per the standard's own comment, and the enum underneath says which convention is in force. We did not rename them to something friendlier on the way in. Renaming is interpretation dressed as decoding — and interpretation is the profile author's job, which is the next thing you will see.”

What to say

“Personal-data detection ran across two thousand detection reports and found nothing. Not because it was switched off — it ran on every record. There is nothing personal in this format to find. A SAPIENT DetectionReport carries position, confidence, classification, behaviour, RF signal. It carries no operator name, no home address, no classification marking, no U.S. Persons determination and no retention basis.”

“That is now three sensing standards in a row — MISB ST 0601 for full-motion video metadata, ASTM Remote ID off the air, and SAPIENT. Sensing standards carry observation, not entitlement. Which tells you where a governance platform's obligations actually begin, and it is not at the sensor.”

One thread does run back to a person: id — the field BSI Flex 335 documents as “ID of the object being reported (e.g. the tail number of aircraft)” — carrying the Remote ID serial an RF node heard on 591 of the 2,000 reports. object_info_cooperative splits the corpus on exactly that line: 591 aircraft identified themselves and 1,409 were painted by radar and said nothing. What the sensor does not report is who the serial belongs to; that needs a registry, and that join is enrichment. It is pseudonymous — it becomes identifying only through a civil aviation registry this platform does not hold — so the profile leaves it undeclared rather than asserting an answer that is jurisdiction-dependent. Silence means “nobody has said”, so the detector keeps looking at it. Remember this field; it carries the whole of Act Three.

The profile that governs the enriched record is refused on this one, by name, with the element each refusal turns on — and the answer arrives before a single record is touched, because whether a control can run is a property of the columns, not of any row. It does not quietly skip §2.3 and hand you a clean-looking output.

What to say

“A container that cannot carry the flag must not be allowed to quietly retire the control. If this platform ran the U.S. Persons control here it would report success on two thousand records and protect nobody, because there is no field in the standard saying who is a U.S. person. Governance obligations attach at enrichment, not at the sensor — and that generalises a long way past drones.”

Read that disclaimer out. The platform does not hold the BSI Flex 335 ICD, so it does not claim conformance to it — but it does validate every record's mandatory fields against the is_mandatory annotations carried in the standard's own .proto files, rather than against a list maintained here that could drift. That check earned itself the day it was written: it caught that report_id was unset on every record.

What to say

“That is our own reader, running the standard's own schema, accepting a file we produced. It is not a SAPIENT-flavoured export — a fusion node would take it.”

“The serial is the field carrying the entitlement. It is pseudonymous, but it resolves to a named person through the registry, and it is the field that reaches a SAPIENT emission — so the profile puts it in the minimisation set, and an unauthorised fusion node does not get a handle on the operator.”

“And the message id is the same in both files. Message ids derive from the profile fingerprint and the row's position, not from a clock, so re-emitting one governed corpus produces identical bytes. Two runs of a release set cannot differ for reasons that are not governed.”

Across the two captures: 456 serials minimised and 135 in the clear for the security desk; none minimised and 502 in the clear for the federal partner. 1,409 detections carry no serial at all in either — those are drones nobody heard a Remote ID broadcast from.

   manifest.json
   airport_security_desk_emission_sapient_detections_….bin   2,000 records

The manifest reports each release's authority, the controls applied, and that mandatory-field validation passed — with conformant: false stated plainly. It also says what it cannot tell you: the two releases hold different record counts, so no per-record comparison is possible. An honest “no answer” rather than a misleading diff. The pipeline runs once per distinct authority, not once per release, so two releases cannot disagree about what was governed.

06

Questions you will get

And short answers that are true

“Is this really SAPIENT, or your idea of it?”

The standard's .proto files are in the repository verbatim with their Crown copyright and Apache-2.0 notice, and decoding runs through a descriptor compiled from them — no hand-typed field table, no generated code in the tree. A test holds the descriptor to its sources, so a .proto change without a rebuild fails the suite rather than the deployment.

“You built a drone corpus last week and only then found the standard.”

Yes — and it is written down. Tuesday's counter-UAS CSV is a hand-rolled version of a SAPIENT DetectionReport and nobody looked first. It is recorded in docs/alternatives-considered.md beside the same mistake made with ODCS. The rule that came out of it is: research the standard before designing a format. Conceding those two is what makes the rest of that document worth reading.

“Can it subscribe to our fusion node?”

Not today. The platform reads uploads, and a capture of length-delimited messages is the same shape as any other file. Live SAPIENT is TCP to the middleware and is separate work — it would not need Kafka, which is ruled out here by name for the laptop requirement, because SAPIENT already ships a broker.

“Why does it say non-conformant?”

Because we do not hold the ICD, and claiming conformance to a document you do not hold is how this goes wrong quietly. What is claimed is what was checked: structurally valid, every mandatory field verified against the standard's own annotations. A missing specification is not a reason to withhold governed data — it is a reason to label it accurately.

“How much of this was code?”

The profile governing the capture is a JSON file. The emission target — which column maps to which field of the standard, and the coordinate-system constants — is a JSON file. What stays code is the walker that turns bytes into values, and what a control does to a record. A target naming a format nothing implements is refused by name at load, with the refusal saying where the behaviour would go.

“What stops the AI getting it wrong?”

Nothing rests on it being right. A machine reading only ever proposes meanings — it cannot mark a field required, write a personal-data declaration, raise a profile's authority, approve anything, or choose which profile governs a run. Each is enforced in code with a test behind it.
