Open source · adversarial AI · deterministic control

AI can argue forever. Decisions cannot.

Decision Gate takes an idea, identifies what must be true, tries to break those assumptions, and then stops. The models generate the arguments; a fixed rule turns the remaining problems into ACT, WAIT, or ABANDON.

Two decisions we actually made show the point. Four unedited live runs on outside decisions show what the system does with a strong adversary, including the parts that do not flatter it.

How it works

Decision 1 — we did not build the healthcare idea

Real decision · healthcare

Build a cardiology-first agent for orders → authorization → scheduling → prep → procedure → results → follow-up.

ABANDON
Why it looked good

The workflow is painful, fragmented, expensive, and full of manual handoffs. A focused AI agent sounded like a strong product opportunity.

What the review found

Fatal problem: companies already sell much of the core workflow we were proposing.

Tennr already moves patients through referrals, insurance requirements, authorizations, diagnostics and scheduling. Honey Health already automates prior authorization for procedures, imaging and diagnostics from requirement detection through submission and follow-up. Silna also automates prior-authorization submission and follow-up.

TennrHoney HealthSilna
Why that matters

The problem is real, but “the problem exists” is not the same as “we have a differentiated product.” We had not shown a clear capability customers could not already buy.

Rule trace
problem = “core workflow already exists in market; differentiation not established”
severity = FATAL
status = UNRESOLVED
matched rule = unresolved FATAL → ABANDON
Decision
ABANDONDo not spend engineering time building this product as proposed. A future healthcare idea would need a clearly different wedge and should be treated as a new decision.

Decision 2 — why we did build Decision Gate

Real decision · this project

Build a small open-source control layer that turns AI-assisted analysis into a bounded, auditable decision.

ACT
What we rejected first

We did not decide to build “another multi-agent debate framework.” Systems for agents debating, critiquing, reflecting and orchestrating already exist. That alone was not interesting enough.

What remained useful

The narrower problem survived the challenge: AI can keep generating objections without ever telling the user when enough analysis is enough. We wanted a control layer that:

1. records the claims and important objections,
2. stops review using an explicit policy,
3. maps unresolved problems to ACT / WAIT / ABANDON with fixed rules,
4. records exactly why the decision was made,
5. reopens only when something materially changes,
6. later compares the reasoning with what actually happened.

Remaining risk

Material but not fatal: the outcome-scoring idea only becomes truly useful after we accumulate enough real decisions and later observe what happened.

That is a reason to measure the project, not a reason to block the MVP.

Rule trace
fatal unresolved problems = 0
blocking unresolved problems = 0
material accepted risk = “needs enough real decisions to score usefulness”
matched rule = no unresolved fatal/blocking problem → ACT
Decision
ACTBuild the smallest MVP, use it on real decisions, and let later outcomes tell us whether the reasoning process is actually useful.
The important difference: healthcare failed because the proposed product itself did not have enough differentiation. Decision Gate survived only after we removed the generic “agents debate” idea and narrowed the project to explicit stopping, deterministic action rules, decision history, controlled reopening, and outcome scoring.

Four live runs, unedited

Claude Opus 5 in both roles, three-round limit, no context beyond the decision sentence. Nothing was touched after the run, including the materiality ratings. Each took four to five minutes and four model calls. The ledgers are in the repository and decision-gate gate <file> recomputes each action from the file alone.

"If resolved" is computed, not narrated: the gate re-run as if the triggering challenges were answered. It separates a decision that is under-evidenced (three WAITs that would become ACT) from one whose framing is wrong (the ABANDON that would only become WAIT).

The one ABANDON

The Adversary's first challenge on the hospital decision is a structural argument, not a risk. Pagers run on a separate radio network with no dependency on hospital IT. An app that replaces them removes the out-of-band channel for exactly the scenarios in which the app is down: ransomware, network core failure, a vendor cloud outage. "Replace" is a different decision from "add", and the claim set never noticed.

Answer that argument, by rescoping to a hybrid as the challenge's own resolves_if proposes, and the gate still says WAIT. Ten BLOCKING challenges remain: Wi-Fi does not reach into MRI suites, which are Faraday cages by design; a one-way paging network produces no delivery telemetry, so the "documented rate of missed pages" the Builder typed as a FACT cannot actually be measured; on-call clinicians are reached at home, outside any hospital coverage survey.

What the four runs showed

Four runs with one model in both roles is a demonstration, not a sample. These observations sit in the repository next to the ledgers, because a reader will find them anyway.

4 of 4 runs hit the round limit

The stop rule never fired

Every round produced at least five consequential challenges. With this Adversary, the budget bounds the review, not convergence. Termination is still guaranteed, which is the point of the rule, but a strong Adversary does not run out of material at three rounds.

92 challenges · 1 FATAL · 44 BLOCKING · 47 MATERIAL · 0 NON_BLOCKING

Nothing was rated non-blocking

The Adversary used the top three rungs of a four-rung scale. Since the gate reads only these ratings, WAIT is close to guaranteed from unedited output. This is the soft spot the design names openly: the model is moved one step back from the decision, not removed from it. Ratings are visible and editable before gating, and a re-rated ledger records that it was.

context: none

The claims are archetypes

With no context supplied, the Builder wrote what would need to be true for a generic instance of each decision, and the Adversary attacked those. Real context, this hospital's pager contract expiry or this team's job inventory, is what would make the claims specific and the challenges sharper.

statutes, mechanisms, cross-claim tensions

The challenges are expert grade, and they compound

Federal-aid tolling restrictions and state anti-diversion clauses on the congestion pilot. DuckDB's single-writer model and an un-optimised Spark baseline on the migration. A GM hired before expansion versus after on the bakery. In later rounds the Adversary extended its own earlier challenges rather than restating them.

The final rule is deliberately simple

IF an unresolved problem would make the idea fundamentally wrong → ABANDON ELSE IF an unresolved problem must be fixed before acting → WAIT ELSE → ACT Important but non-blocking uncertainty is recorded as accepted risk. The matched rule and the problems that triggered it are written into the ledger.

Run the actual system

This website is a static explanation of the project. It does not pretend to run the Python/model backend. The executable UI and model runner are in the repository.
